## 한국투자증권 (Phase 5)

시세 조회만 한다. 계좌번호는 읽지 않고, 주문 기능은 없다. 실시간 화면은 보는 용도이고, 분석의
정본은 장 마감 뒤 REST로 받는 1분봉이다. 연결이 끊기거나 서버를 켜지 않은 날에도 기록에는 구멍이
나지 않는다.

**공급자의 의미는 실제 호출로 정했다(5-0, 2026-09-25, 12회).** 이 12회는 쿼터 원장이 생기기 전 스크립트로 호출해서 원장에 없다.

| 확인한 것 | 결과 |
|---|---|
| 종목 분봉 시각 `HHMMSS` | **그 분의 시작.** `090000` 봉이 있고 연속매매 마지막 봉이 `151900`이다. 우리 기준은 `ts` = 분 시작, `available_at` = 분 끝 |
| 하루 봉 수 | 매 분 체결이 있으면 381개가 최대다 = 연속매매 380(09:00~15:19) + 종가 단일가 1(15:30). 15:20~15:29에는 봉이 없다(삼성전자 9/23에서 381개 확인) |
| 09:00 봉 | 장전 동시호가 체결이 들어간다(삼성전자 9/23: 63만 주) |
| 체결 없는 분 | 봉이 없다. 허봉 옵션 Y/N의 결과가 같았다(원림 9/23, 69개 봉) |
| 과거 분봉 페이지 | 호출당 120개, 커서로 넘기면 커서 봉이 다시 나온다(중복 제거 필요). 09:00을 지나면 전날 시간외 봉(19:59까지)으로 이어지므로 날짜와 09:00~15:30으로 거른다(삼성전자 9/23, 4페이지) |
| 업종(지수) 분봉 | **최근 세션의 마지막 약 100분만, 날짜 지정 불가, 다음 페이지 없음**(9/25 휴장일에 KOSPI·KOSDAQ 조회, 9/23 13:53~15:32). 과거를 받을 수 없어 장중에 나눠 받아 하루를 잇는다. 확정 종가는 `999999` 행 |
| 속도 초과 오류 | 일부러 일으키지 않았다(한도 원칙). 공식 예제의 `EGW00201`로 처리한다 |
| 웹소켓 실제 체결 데이터 | 첫 개장일(9/28)에 확인 |

**토큰은 받아서 다시 쓴다.** KIS는 토큰을 1분에 한 번만 발급하고 하루 재사용하라고 한다. 그래서
발급받은 토큰과 웹소켓 접속키를 만료 시각과 함께 `kis_credential`에 두고 만료 10분 전까지 다시
쓴다. 발급은 프로세스 사이에서 잠금으로 한 번에 하나씩 하고, 마지막 발급이 65초 안이면 KIS에
묻기 전에 거절한다. 앱키·시크릿은 `.env`에만 있고 DB로 복사하지 않는다. 오류와 로그에는 KIS의
코드와 메시지만 들어가고 키·토큰·헤더는 들어가지 않는다(가짜 서버로 실패 응답을 받았을 때 예외와 로그를 테스트가 확인한다).
메모리에 들고 있는 토큰도 저장본과 같은 여유(만료 10분 전)에서 버린다. KIS가 토큰을 거절하면 그 토큰만
만료 처리한다. 다른 프로세스가 방금 받은 토큰까지 무효로 만들지 않기 위해서다.

**호출은 보내기 전에 예약한다.** 모든 REST 호출은 `kis_rest` 쿼터에 먼저 예약되고 **2초에 1회**로
속도를 맞춘다(시작할 때 몰아서 보내지 않음). 실전 계좌는 초당 20회라고 알려져 있지만, 2026-09-25에
이 앱키는 0.1초 간격 두 번째 호출에서 `EGW00201`로 거절됐고, **초당 1회를 몇 분간 일정하게 유지할 때도
가끔 거절됐다**(원장 기준 분당 60회). 신규 키의 낮은 한도나 서버 쪽 도착 간격의 흔들림으로 보이지만
확인하지 못했다. 그래서 지금은 **2초에 1회**(`KIS_RATE=0.5`)로 두고, 실제 한도를 확인하면 올린다.
이 속도는 클라이언트 하나 기준이다. REST 호출은 워커 한 곳에서만 한다. KIS가 `EGW00201`(초당
한도 초과)로 거절하면 우리 속도 조절이 틀렸다는 뜻이므로 조용히 재시도하지 않고 실패로 남긴다.
만료됐다는 응답(`EGW00123`)을 받으면 저장된 토큰을 만료 처리하고 한 번만 다시 발급받는다.

## 1분봉 정본 (5-3)

```
python -m app.cli minutes --backfill 60 --max-calls 3000   # 관심 종목의 1분봉. 오늘(마감 후)과 과거 60세션
python -m app.cli collect --source index_minute           # KOSPI·KOSDAQ 1분봉, 최근 약 100분
```

**종목의 하루는 장 마감 뒤 한 번에 받는다.** 과거 분봉 호출로 15:30부터 거꾸로 페이지를 넘긴다. 다음
페이지는 본 것 중 가장 오래된 봉에서 시작하고, 그 봉이 다시 오므로 시각으로 중복을 없앤다. 09:00에
닿거나 전날 봉이 나오면 그날은 COMPLETE다. 봉을 받다가 빈 페이지가 오면 끝났다는 증거가 아니므로
PARTIAL이다. 커서가 안 움직이거나 페이지 상한(8)에 걸리면 PARTIAL이고,
그날은 분석하지 않고 다음 실행에서 다시 받는다. 그날 봉 대신 전날 봉이 오면 그날은 정말 봉이 없는
것이므로 EMPTY(거래정지 등)다. 아무것도 안 온 응답은 증거가 못 되어 PARTIAL로 두고 다시 받는다. 오늘
날짜는 EMPTY로 확정하지 않는다(마감 직후 아직 안 줄 수 있다). 한 종목의 잘못된 응답이나 연결 끊김은 그
종목·날짜만 ERROR로 남기고 나머지를 계속 받는다. 속도 초과 거절은 지금처럼 실행 전체를 멈춘다.
날마다 `minute_fetch`에 한 행을 남긴다. 09:00~15:30만 저장한다.

**KIS를 부르는 실행은 한 번에 하나다.** 속도는 프로세스마다 따로 맞추는데 KIS는 앱키 단위로 센다.
손으로 돌린 백필과 워커가 겹치면 두 배 속도가 된다. 그래서 분봉과 지수 수집은 공용 잠금을 잡고,
이미 누가 잡고 있으면 건너뛴다(SKIPPED).

**지수는 장중에 나눠 받는다.** 업종 분봉은 과거 날짜를 받을 수 없고 최근 약 100분만 준다. 그래서 워커가
10시부터 15시까지 매시 정각과 15:40에 받아 하루를 잇는다. 09:00~15:30의 391분이 다 모여야 그날이
온전하다. `888888`·`999999`는 분이 아니라 요약 행이라 버린다. 지수 분봉은 과거로 채울 수 없으므로
시작한 날부터만 있다. 지수 분봉의 시각 표기가 종목과 같은 "분 시작"인지는 아직 확인하지 못했다.
9/23 지수 자료에는 15:31·15:32 행도 있었고, 15:30 행 종가(7078.93)가 확정 종가(`999999`, 7080.92)와
달랐다. 첫 개장일(9/28)에 09:00 부근 행으로 확인한다. 그 전까지도 `available_at`은 늦게 잡히는 쪽이라
미래 정보가 섞이지는 않는다.

**별도 작업이다.** 16:20에 관심 종목의 오늘 분봉과 과거 백필(하루 최대 1,000회, 2초에 1회라 약 35분)을 받는다. 매일 루프
(16:40)와 따로 두어, 새 코드의 실패가 검증된 채점과 포워드 기록을 끊지 않게 했다.

**과거 분봉은 기준선 전용이다.** 과거 60세션의 1분봉으로 알 수 있는 것은 이 종목의 평소 시간대별
거래량과 변동성이다. 우리 판단이 맞았는지는 장전 관찰 목록이 생긴 날부터의 기록으로만 잰다. 과거
분봉에는 그날 우리가 그 종목을 골랐다는 기록이 없기 때문이다. 또 지금 관심 있는 종목의 과거만 받으므로,
기준선은 "이 종목들이 원래 어떤 종목인가"를 말할 뿐이다.

첫 백필(2026-09-25): 첫 백필은 744회 뒤 서버가 연결을 끊어(`RemoteProtocolError`) 옛 코드에서 전체가
멈췄고, 이 일로 종목·날짜 단위 오류 격리를 넣었다. 그때까지 9/15~9/23의 215일치가 완전, 18일치가 빈
날이었다. 빈 날은 세 종목(삼부토건 7일, 에이비온 6일, 랩지노믹스 9/16~9/22)에 몰려 있어 거래정지로
보이지만 확인하지 못했다.

첫 실행(2026-09-25, 9/23 하루): 35종목에 117회, 11,017봉. 완전 33, 빈 날 2(에이비온, 삼부토건),
완전한 날의 봉 수 중앙값 379(최소 54, 최대 381). 삼성전자의 분봉 거래량 합은 18,598,185주였다.

## 장중 분석과 누적 보고서 (5-5, 5-6)

```
python -m app.cli intraday --analyze   # 온전히 들어온 날을 요약하고 보고서를 출력
python -m app.cli intraday             # 보고서만. 읽기만 한다
```

**종목의 하루를 1분봉으로 요약한다(`intraday_summary`).** 16:20 분봉 수집 뒤 같은 작업에서 돈다.
- 시가→종가 수익률
- 사후 최대 상승(MFE)·최대 하락(MAE): **사후 값이지 먹을 수 있는 수익이 아니다**
- 고가·저가 시각, 고점까지 걸린 분
- VWAP(대표가 (고+저+종)/3의 거래량 가중) 대비 종가
- 1분 로그수익률로 잰 실현 변동성
- 가장 거래가 많았던 분: 09:00 시가 동시호가 봉과 15:30 종가 봉은 뺀다. 경매 체결량이 몰려 매일 이긴다
- 30분 구간 13개(09:00~15:30, 15:30 봉은 마지막 구간)마다 수익률과 거래량 비중

첫 한 시간 수익률(시가 → 10시 전 마지막 종가)은 분봉에서 직접 잰다. 30분 구간 두 개를 이어 붙이면
구간 사이의 움직임이 빠진다. 시가가 없어 잴 수 없는 날은 UNMEASURABLE로 남기고 다시 계산하지 않는다.

시장 비교는 그 종목의 지수(KOSDAQ 종목은 KOSDAQ, 나머지는 KOSPI)다. 16:20 분석은 그날 지수 일봉(16:40
매일 루프가 받는다)보다 먼저 돌기 때문에, 시장 값이 빈 날은 다음 분석 때 지수 일봉이 들어와 있으면
시장 값만 채운다. 그날의 다른 측정값은 그대로다. 2026-09-22는 yfinance에 KOSPI·KOSDAQ 일봉이 없어서
아직 비어 있다. 지수 1분봉이 391분 다 모인 날은
구간별로도 비교하고, 아닌 날은 일봉(yfinance)으로 하루 단위만 비교한다(`market_source`). 하루치가
온전하지 않은 날은 상태만 남기고 수치를 계산하지 않는다. 나중에 다 오면 전체 분석으로 바뀐다. 재는
방식이 바뀌면 `analysis_version`을 올린다.

**보고서는 두 부분이다.**
- **기준선:** 우리가 골랐는지와 상관없이 기록된 모든 온전한 날로 만든다. 구간별 평균 거래량 비중과
  |수익률|, 그날 고점이 나온 구간의 분포, MFE·MAE 중앙값이다. **이 종목들이 원래 어떻게 움직이는지를
  말할 뿐 우리 선택의 성과가 아니다.**
- **아침 목록 판단:** `PREOPEN_V2` 목록에 오른 종목의 그날만으로 잰다. 질문(H1~H5)은 이유 코드와
  순위만 보므로 V2에서도 그대로이고, 20일·60일도 V2 기록으로 센다.

첫 계산(2026-09-25, 9/8~9/23 백필분, 357종목일, 12거래일):
- MFE 중앙값 +1.26%, MAE 중앙값 −1.56%
- 09:00~09:30 구간이 하루 거래량의 16.1%를 차지하고, 그날 고점의 49%가 이 구간에서 나왔다
  (시가 동시호가가 들어 있는 구간이다)
- 이 수치도 관심 종목의 과거만으로 만든 것이라 이 종목들에 대한 이야기다

**아침 목록이 답할 질문은 기록이 비어 있을 때 고정했다(`app/scoring/intraday_review.py`).**

| | 질문 | 비교 |
|---|---|---|
| H1 | 좋은 뉴스로 오른 종목이 그날 목록 평균보다 낫다 | 시가→종가 |
| H2 | 그날 목록 평균이 나쁜 뉴스 종목보다 낫다 | 시가→종가 |
| H3 | 검색 급증 종목이 첫 한 시간에 나머지보다 낫다 | 09:00~10:00 |
| H4 | 1~10위가 11~40위보다 낫다 | 시가→종가 |
| H5 | 목록이 그 지수보다 낫다(종목마다 자기 지수 대비) | 시가→종가 초과 |
| H6 | 공시 이유 종목을 9시 시가에 사서 10시 전에 팔면 평균이 0보다 크다(비용 전) | 09:00~10:00 |
| H7 | 목록 전체를 같은 방식으로 사고팔면 평균이 0보다 크다(비용 전) | 09:00~10:00 |

H6·H7은 2026-09-26, 첫 목록이 나오기 전에 더했다. 소유자의 단타는 9시 시가에 사서 늦어도 10시 전에
판다. H1·H2·H4·H5는 시가→종가라 그 시간대를 재지 않는다. 과거 3개월 공시 종목으로 비슷한 질문을 잰
공시 이벤트 분석 v2와 함께 읽는다. 다만 모집단이 다르다. 여기 첫 1시간은 그날 **첫 봉**의 시가에서
재므로 첫 봉이 09:02인 날(v2가 뺀 날)도 들어간다.

모두 **날짜별로 짝지어** 잰다. 두 그룹이 다 있는 날의 평균 차이가 관측 하나다. 20일이면 읽기만 하고,
60일이 되면 **처음 60일로 한 번만** 판정한다. 차이가 양수이고 t ≥ 2이고 앞·뒤 절반 모두 양수면
"성립"이다. 성립해도 아무것도 바뀌지 않는다. 다음 전략 버전을 제안할 근거가 될 뿐이다.

## 실시간 차트 (5-4)

```
python -m uvicorn app.main:app --app-dir backend --port 8000   # API (LIVE_FEED_ENABLED=true일 때 실시간 피드 포함)
npm --prefix frontend run dev                                   # 화면. "오늘의 관찰" 탭
```

**보는 용도이고 기록이 아니다.** 한국투자증권 실시간 체결(`H0STCNT0`)을 받아 브라우저로 보낸다. 체결이
들어올 때마다 진행 중인 1분 캔들이 바로 바뀐다. "1초봉"으로 바꾸면 화면을 연 뒤부터 1초봉으로 본다.
저장하지 않는다. 분석하는 정본은 장 마감 뒤 REST로 받는 1분봉이다.

**연결은 하나다.** API 프로세스 안의 게이트웨이 하나가 Postgres advisory lock(`kis_ws_feed`)을 잡은
동안만 한국투자증권 소켓을 연다. uvicorn 워커를 여러 개 띄워도 소켓은 하나이고, 잠금을 못 잡은
프로세스는 화면에 "다른 프로세스가 실시간 연결을 쓰는 중"이라고 표시한다(API 상태 코드는
`another process holds the KIS feed`). 한 연결의 구독은 40개까지다
(예제 코드 기준). 앱키당 세션 수 제한은 확인하지 못했다. 그래서 하나만 여는 것을 우리 정책으로 둔다.

**장 시간에만 연다.** 한국 거래일 08:55~15:35에만 연결하고, 그 밖에는 대기한다(휴장일인 9/25에
"idle (outside the session)"을 확인했다). 끊기면 10초부터 5분까지 늘려 가며 다시 붙는다. 접속키는
5-1의 저장·재사용 규칙을 따른다. PINGPONG에는 한국투자증권 예제처럼 같은 내용으로 답한다.

**무엇을 보여주나.**
- 구독 대상은 오늘 아침 목록(최대 40)이다. 같은 날 V1과 V2가 함께 있으면 V2를 고른다. V2 목록이
  0개면 "오늘 조건에 맞는 종목 없음"이고 추적 종목으로 대신하지 않는다. 목록 자체가 없을 때(생성 실패)만
  추적 한국 종목을 참고용이라고 표시해서 보여준다.
- 화면 머리에 "관찰 목록 — 매수 추천이 아닙니다"를 적고, 종목마다 관찰용 점수와 점수 보류 사유,
  사전 수집을 못 한 종목(`SKIPPED_CAP` 등)을 표시한다.
- 종목마다 **아침에 본 이유**(이유 코드, 오버레이, 검색 급증, 국면)를 차트 옆에 항상 띄운다.
- 장중에 늦게 연결해도 그날 09:00부터 보이도록, 오늘 앞부분 1분봉을 REST로 한 번 채운다. 08:55처럼
  개장 전에 연결하면 채울 것이 없어 부르지 않는다. 5-1과 같은
  쿼터·2초 1회 속도·KIS 실행 잠금을 지킨다. 잠금은 종목마다 잡았다 놓는다. 그래야 과거 날짜로 채울 수
  없는 매시 지수 분봉 수집이 그 사이에 돈다. 한 종목의 실패는 그 종목만 비운다.
- 구독이 거절되면 상태에 "실시간 수신 중 (구독 거절 N개)"로 보인다.
- 브라우저 연결이 끊기면 서버는 다음 체결을 기다리지 않고 바로 정리한다(장 밖에는 체결이 오지 않아,
  그렇지 않으면 서버 종료가 멈췄다). 화면은 3초 뒤 다시 연결한다.

`LIVE_FEED_ENABLED=true`일 때만 켜진다. 하루 종일 소켓을 잡는 일이라 요청할 때만 연다.
