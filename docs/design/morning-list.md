## 장전 관찰 목록 (5-2)

> 아래는 V1(`PREOPEN_V1`)의 설계다. 실제 목록은 한 번도 만들지 않았고, 워커는 9/28부터 V2를 만든다.
> 목록을 얼리는 방식(하루 하나, 개장 뒤 거부, 그때의 숫자 그대로, 입력 상태 함께)은 V2도 같다.
> 달라진 것은 다음 절 "단타용 아침 흐름"에 있다.

```
python -m app.cli watchlist           # 가장 최근 아침 목록. 읽기만 한다
python -m app.cli watchlist --take    # 오늘 목록이 없으면 지금 고정한다
```

**아침 일정.** 08:00 뉴스·공시·검색 추세 수집(약 10분) → **08:30 LLM 판정·해석**(09:30에서 옮김) →
**08:50 관찰 목록 고정** → 09:00 개장. 해석을 개장 뒤에 하면 아침 뉴스가 아침 선택에 들어가지 못한다.
마감 신호에도 더 일찍 반영될 뿐 손해가 없다.

**고른 이유를 그때의 숫자 그대로 얼린다.** `watchlist_snapshot`은 거래일마다 하나이고 고치지 않는다.
그날 두 번째 실행은 아무것도 하지 않고, 데이터베이스의 유일 제약도 두 번째를 거부한다. **개장(09:00)
뒤에는 만들지 않는다.** 장중 정보로 고른 목록이 그날의 기록이 되면 그날 성과로 판단을 잴 수 없다.
08:50을 놓친 날은 목록이 없다. 종목마다(`watchlist_member`) 순위 1~40, 선정 이유 코드 목록,
그리고 08:50 당시의 오버레이 점수와 사건, 검색 급증, 발굴 점수, 국면, 전날 마감 신호의 총점·기술·재무
점수(그 신호의 판단 시각과 함께)를 남긴다. 나중에 뉴스를 재판정하거나 모델을 바꿔 현재 값이 달라져도
"그날 왜 골랐는가"는 바뀌지 않는다. 추적하지 않는 종목은 신호가 없어 점수 칸이 비고, 비어 있다는 것
자체가 기록이다.

**선정 규칙 v1(`PREOPEN_V1`)은 코드에 먼저 고정했다.** 대상 풀은 관심 종목(추적 + 최근 후보), 그
순간의 발굴 후보, 지난 세션 이후 사건 공시가 있는 종목이다. 이유는 여러 개가 함께 붙는다.

| 코드 | 조건 |
|---|---|
| `DISCOVERY_SURGE` | 그 순간 뉴스 급증 후보 |
| `POSITIVE_NEWS_OVERLAY` / `NEGATIVE_NEWS_OVERLAY` | 오버레이 +1점 이상 / −1점 이하 |
| `DISCLOSURE_EVENT` | 지난 세션일부터 어제까지 접수되고 08:50까지 저장된 사건 공시 |
| `SEARCH_SURGE` | 검색이 이전 수준의 2배 이상 |
| `TRACKED_HIGH_SCORE` | 추적 종목이고 전날 마감 신호가 BUY_INTEREST |
| `TRACKED` | 추적 종목(그 순간 기준. 나중에 승격된 종목은 아니다) |

순서는 이유 수(`TRACKED`는 빼고 셈) → 오버레이 크기 → 검색 급증 → 발굴 점수 → 종목 번호다. 같은
입력이면 항상 같은 순위가 나온다. 최대 40개이고, 이유가 있는데 못 들어간 수도 남긴다. 기준값은 시스템의
다른 곳과 같다(오버레이 ±1점, 검색 2배).

**공시는 "어제까지 접수된 것"으로 본다.** 공시 목록은 접수일만 주기 때문에 오버레이는 공시를 다음 세션
개장(09:00)부터 쓴다. 그러면 08:50에는 어제 저녁 공시도 보이지 않는다. 하지만 어제 날짜로 접수된 공시는
어제 자정까지 공개된 것이 확실하다. 그래서 관찰 목록은 접수일이 오늘보다 이르고 08:50까지 저장된 공시를
별도로 읽는다. 오버레이의 규칙은 그대로 둔다.

**아침 입력이 무엇이 빠졌는지 함께 얼린다.** 스냅샷의 `inputs`에 담는 것:
- 뉴스 스윕 실행 상태와 목록 종목 중 오늘 아침 스윕을 받은 수
- 오늘 아침 LLM 호출 수와 상태별 수
- 검색 추세와 공시 수집의 상태

하나가 실패해도 목록은 만든다. 뉴스 스윕 상태가 매일 PARTIAL(기사가 많은 274종목이 1페이지 상한에
걸림)이라 실행 상태만으로는 판단이 안 되기 때문에, 종목별로 실제 읽은 시각(`news_swept_at`)도 남긴다.

아침 목록에 오른 종목은 그날 저녁부터 열흘간 1분봉 수집 대상에 들어간다. 그날 분봉이 한 번 실패해도
다음 날 다시 받는다.

## 단타용 아침 흐름 (`PREOPEN_V2`)

```
python -m app.cli preopen status                 # 오늘 후보 풀과 단계별 상태. 읽기만 한다
python -m app.cli preopen dry-run --asof 2026-09-24T08:50+09:00   # 참고용 재계산. 쓰지 않는다
python -m app.cli watchlist --take               # 오늘 V2 목록이 없으면 지금 고정한다
```

**목록은 그날 사건이 있는 종목만으로 매일 새로 만든다.** 이 목록은 매수 추천이 아니라 오늘 확인할
가치가 있는 **관찰 목록**이다. 화면에도 그렇게 적는다. V1은 추적 종목이라는 이유만으로 조용한 종목도
넣었다. V2에서 목록에 들어가는 이유는 뉴스 급증, 좋은 뉴스(+1 이상), 나쁜 뉴스(−1 이하), 사건 공시,
검색 2배 이상뿐이다. 추적 여부와 전날 점수는 들어가는 이유가 아니고 종목 행의 속성으로만 남는다. 조용한 날은
0개가 정상이고, 0개인 목록도 그대로 저장한다. V1 코드는 남겨 두지만 워커는 더 만들지 않는다.

**선정 3(2026-10-06 목록부터 — 10/5는 휴장, `selection_version` 3): 40개를 고른 뒤 두 묶음을 뺀다.** 그날 08:35 판단 점수(합계 ÷ 참여
가중치 합, 신호 탭·카톡의 "판단"과 같다)가 40 미만인 종목(`LOW_SCORE`)과 전 거래일 종가가 +15% 이상 오른 종목
(`PREV_SURGE`, `prev_limits_many`, 목록을 얼리는 시각까지 들어온 일봉)이다. 우리 목록 5일(9/28~10/2)과 3개월 공시 표본에서
두 묶음은 9시 시가 매수가 꾸준히 마이너스였다(소유자 결정, 2026-10-02). 빈자리는 41위 이하로 채우지 않고, 순위도 다시
매기지 않는다(남은 목록 순위에 빈칸이 생긴다 — H4 "1~10위 vs 11~40위"의 뜻을 지키려고). 판단 보류·채점 실패로 점수가
없거나 전일 봉이 없으면 빼지 않는다(채점이 멈춘 날 목록이 비지 않게). 뺀 종목도 원래 순위 그대로 `watchlist_member` 행으로
남기고 `excluded_reason`에 이유를 적는다. 오늘의 관찰·신호 탭·카톡·증권사 의견 수집은 이 칸이 빈 행만 쓰고, 분석(H1~H7,
list-review, 전략 실험실, "우리 목록 보통" 기록)과 1분봉 수집은 제외 전 40개를 계속 본다. 그래야 빼는 규칙이 계속 맞는지
잴 수 있다. 목록 기록의 `inputs.exclusion`에 규칙별 적용 여부(점수 단계가 끝나지 않았으면 점수 규칙은 적용 안 됨)와 뺀 수가
남는다. 5일치에 적용하면 목록 40개 중 하루 11~16개가 빠지고 24~29개가 남는다(9/28 12개, 9/29 16, 9/30 12, 10/1 13, 10/2 11 — 대부분 점수,
전일 급등은 하루 1~7개). 잴 수 있던 종목으로는 남은 목록 -0.25%, 뺀 종목 -2.31%(+2.5% 익절·손절 없음, 9시 시가·비용 0.30%, 날짜 기준).
목록은 여전히 관찰 목록이지 매수 추천이 아니다. `preopen dry-run`은 제외를 적용하지 않는다.

| 시작 | 단계 | 들어가는 조건 |
|---|---|---|
| 07:00 | 체인: 전체 스윕 → 후보 풀 확정 → 검색 추세 → 사전 수집 → LLM | 거래일, 개장 전 |
| 08:30 | 보충 스윕(풀 종목만) → 보충 기사 LLM | 풀 확정, 07:00 LLM 단계 종료 |
| 08:35 | 그날 관찰용 점수 | 풀 확정, 사전 수집 단계 종료 |
| 08:38 | V2 목록 고정 | 없음. 빠진 단계는 기록만 한다 |

**2026-10-02부터 점수 08:35·목록 08:38(그 전 08:40·08:50).** 08:44 아침 카톡이 개장 전 판단 시간을 갖게 당겼다.
선정 규칙과 뉴스 마감(08:30 보충)은 같다. 9/28~10/1을 08:38 기준으로 다시 계산해 보니 선정·순위·이유가 모두 같았고
오버레이 점수만 감쇠 시각 차이로 0.01 미만 달랐다(08:34~08:50에 새로 들어오는 수집이 없다). 기다림 한계는 08:36이고(60초 간격이라
실제 마지막 시작은 08:36:59), 늦은 발화는 보충 4분·점수 2분까지만 받는다. 목록이 이미 얼었으면 점수·보충은 건너뛴다.

**시각은 시작 신호일 뿐이다.** 07:00 체인은 한 작업 안에서 순서대로 돈다. 08:30과 08:35 작업은 앞
단계가 끝났는지를 `preopen_pool.stages`로 확인하고, 아직이면 1분마다 다시 본다. 08:36까지도 안
되면 건너뛰었다고 기록한다. 08:38 목록은 무엇이 빠졌든 만든다. 07:00 체인이 풀을 얼리지 못했으면
그 자리에서 `DEGRADED_FALLBACK` 풀을 만들어 얼린 뒤 목록을 만든다. 정상일 때든 장애일 때든 목록은
`pool_id`로 자기 풀을 가리킨다. 체인의 한 단계가 예상 밖 오류를 내면 그 단계만 FAILED로 남기고
(추적 정보는 로그에) 다음 단계로 간다. 아침 체인이 멈추면 그날 목록의 입력이 통째로 빠지기 때문이다.
풀조차 얼리지 못하면 목록을 만들지 않는다. 0개 목록이면 화면이 장애를 "오늘 조건에 맞는 종목 없음"으로
보여 주기 때문이다. 늦게 깬 체인은 개장했거나 V2 목록이 이미 있으면 남은 단계를 건너뛰었다고 적고
멈춘다. 단계 기록은 네 작업이 서로 다른 세션에서 같은 행에 쓰므로, 쓸 때마다 행을 잠그고 다시 읽는다.
처음 사본에 덧써 저장하던 첫 구현에서는 끝난 LLM 단계가 RUNNING으로 되돌아가는 순서가 재현됐다.
멈추는지는 단계와 단계 사이에서만 본다. 08:50 직전에 시작한 사전 수집이나 LLM은 끝까지 돌고, 그동안
풀 종목 행을 다시 쓸 수 있다. 목록은 08:50의 값을 자기 행에 복사해 두므로 목록 기록은 바뀌지 않는다.

**후보 풀(`preopen_pool_member`).** 발굴 상위 30(V2에서만 30이고 전역 기본값 20은 그대로), 직전
거래일부터 어제까지의 사건 공시 종목, 관심 종목(추적 + 최근 3일 후보)이다. 관심 종목은 뉴스·검색
이유를 보려고 넣을 뿐이다. 풀 크기는 정해져 있지 않아 실제 `pool_count`를 남긴다. **발굴 점수는
07:00 값으로 얼린다.** 08:50에 발굴을 다시 돌리면 08:30 보충 기사가 풀 종목에만 더해져 급증이
부풀려진다. 보충 기사는 뉴스 점수(LLM 해석)로만 들어간다.

**순서.** 이유 수 → 뉴스 점수 크기 → 검색 배수 → 발굴 점수 → 공시 강도 → 종목 id. 공시 강도는 V2에서
더했다. 공시만 있는 종목은 앞의 숫자가 모두 비어 있어, 목록이 40개로 차면 누가 남을지를 종목 id가
정했다. 공휴일 뒤 아침처럼 공시가 몰리는 날 그 순서는 사실상 임의다. 강도는 공시 분류 규칙의 것을
쓴다(자사주 취득 0.6, 공급계약 0.5, 현금배당 0.3 …).

**사전 수집은 "있느냐"가 아니라 "쓸 만큼 최신이냐"로 판단한다.** 임시 순위(뉴스 점수 없이 발굴·공시·
검색만으로 매긴 V2 순위)가 높은 종목부터, 하루 150종목까지(풀 전체, 2026-09-28에 20에서 올림) 받는다. 가격은 직전 거래일 종가가 있어야
최신이다. 처음 받는 종목은 5년치, 있던 종목은 최근 한 달을 받는다. 재무는 그 종목으로 DART에
마지막으로 닿은 지 7일(기존 재무 신선도 기준과 같은 값)이 지났으면 다시 받는다. 반기·분기 보고서는
보지 않는다. 재무 수집기가 사업보고서만 읽어서, 새로 받아도 점수가 바뀌지 않는다. 넘친 종목은
`SKIPPED_CAP`으로 남고, 점수가 없다고 목록에서 빠지지 않는다. 추적 등록은 하지 않는다. 상태는
`FETCHED` / `FRESH` / `SKIPPED_CAP` / `FAILED` / `NO_DATA`다.

**실행 이름은 기록을 읽는 쪽이 헷갈리지 않게 짓는다.** 수집 기록 조회(`last_success`,
`last_full_success`)는 이름 앞부분으로 찾는다. 사전 수집을 `DART_…`로 남기면 몇 종목짜리 실행이 추적
종목 전체의 재무 신선도 판정을 속인다. 그래서 `PREFETCH_`로 시작한다. 보충 스윕도 같은 이유로
`NAVER_NEWS_…`가 아니라 `PREOPEN_NEWS_SUPPLEMENT`다. 그렇게 부르면 풀 종목만 본 보충의 SUCCESS가 전체
스윕의 워터마크를 끌어올린다. 같은 이유로 추적 종목의 재무 확인 시각은 `last_success("DART")`가 아니라
`DART_FUNDAMENTAL` 실행만 이름 그대로 본다. `LIKE 'DART%'`는 공시 수집(`DART_DISCLOSURE`)까지 세서,
07:00 체인이 공시를 받는 순간 추적 종목의 재무가 늘 "오늘 확인함"으로 보인다. 16:40 추적 종목 채점은
2026-09-28에 멈췄다(수동 재채점만 그 함수를 쓴다, [알려진 한계](../limitations.md#알려진-한계)). 보충은 워터마크를 묻지 않고 오늘 07:00 스윕이 시작한 시각부터 읽고, 그
읽은 구간 기록은 발굴 기준선에 들어가지 않는다.

**LLM은 한 번에 한 실행, 합계 예산 안에서.** 판정과 해석을 합쳐 07:00은 400건(판정은 100건까지), 08:30은 50건
(판정은 25건까지)이다(2026-10-02부터, 그 전 100·30건이고 판정 상한이 없었다). 판정 대기가 흔한 낱말 이름 몇 종목(SBS·LS 등)에
수천 건 쌓여 판정이 예산을 다 쓰고 해석이 0건이던 날(10/1)이 있었다. 두 단계 모두 종목마다 돌아가며 고른다(`spread_hits`:
각 종목의 가장 새 기사 하나씩, 그다음 둘째씩, 72시간 안의 기사 먼저) — 10/1 자료로 후보 선택만 재현하면(실제 해석 결과 아님) 해석 후보가 닿는
풀 종목이 44개에서 150개 전부가 된다(후보는 최신순 최대 2만 건까지 받아 나눈다, 0.5초). 07:00 단계는 08:25, 08:30 단계는 08:36 뒤로 새 호출을 시작하지 않는다(늦게 깬 날 보충과 목록 고정을
밀어내지 않게). 해석이 있는 종목이 늘어 뉴스 오버레이 사유를 얻는 종목도 늘 수 있다 — 목록 구성이 달라지는 변경이다
(기준선: 오버레이 |점수|≥1 종목 9/29 10 · 9/30 18 · 10/1 16). 구독 7일 사용률 멈춤선은 0.95다(2026-10-01 소유자 선택,
그 전 0.8 — 소유자 본인 사용으로 0.79여서 아침마다 멈출 참이었다. 5시간 멈춤선 0.5는 그대로).
처음 구현은 판정 100건과 해석 100건을 따로 세서 최대 200건이었다. 08:30은 보충 스윕 직전의 최대
`news_query_hit.id`를 기록해 두고 그 뒤에 생긴 종목-기사 쌍만 넘긴다. `created_at`은 트랜잭션 시작
시각이라 경계로 쓰기에 불안하다. 모든 LLM 실행(워커·CLI·감사)은 공용 잠금 `llm_run`을 잡고, 이미 누가
잡고 있으면 기다리지 않고 멈췄다고 보고한다. `LLM_SCHEDULE_ENABLED`가 꺼져 있으면 LLM 단계는 SKIPPED다.

**그날 관찰용 점수(08:35)는 `signal`에 쓰지 않고 풀·목록 행에 남긴다.** 선정 3부터는 판단 점수 40 미만이 목록에서 빠지는
기준이기도 하다(위). 2026-09-28부터 이 점수가 신호다(추적 종목
매일 채점은 그날 멈췄다). 요인 분해와 근거 문장은 `score_detail`(`/api/signals`의 신호와 같은 모양)에 남긴다.
기존 엔진(기술 60 + 재무 40)을 그대로 쓰고, 추적 종목도 같은 규칙으로 다시 계산한다. 비교군은 그 시점의 추적 한국 종목으로 고정하고 수와
해시를 남긴다. 시점은 셋으로 나눠 남긴다.
- `price_data_asof`: 기술 점수가 읽은 직전 거래일 종가
- `fundamental_data_asof`: 점수가 쓸 수 있던 가장 늦은 재무가 쓸 수 있게 된 시각
- `evaluated_at`: 08:40

엔진은 재무를 가격 일봉과 같은 순간(직전 종가)에 맞춰 읽는다. 공시의 `available_at`은 다음 개장이라
전날 장 마감 뒤 공시는 어차피 09:00에야 쓸 수 있으므로, 08:40까지 쓸 수 있는 재무와 같은 집합이다.
재무 신선도는 추적하지 않는 종목이면 전체 DART 실행이 아니라 그 종목의 확인 시각으로 판단한다.

**목록에 함께 얼리는 입력 상태(`inputs`).** 기존 항목(뉴스·LLM·검색 추세·공시)에 풀 상태와 단계별 상태,
`pool_count`, 사전 수집 상태별 개수, 보충 스윕 상태를 더했다. 종목 행에는 관찰용 점수와 세 시점,
비교군 수·해시, 사전 수집 상태, 점수 보류 사유가 들어간다(`score_source = PREOPEN`).

**한도.** 네이버 검색은 최근 24시간으로 센다. 전날 16:00, 오늘 07:00, 오늘 16:00 스윕이 한 창에
걸린다고 보고 1페이지 기준 약 8,000회(2,648 × 3 + 보충 풀 종목 수, 계산값)로 예산 12,500 안이다.
2페이지로 올리면 최악에 예산을 넘으므로 지금은 올리지 않는다. DART 사전 수집의 종목당 호출 수는 아직
실측하지 않았다. 모든 호출은 기존 쿼터 원장을 거친다. 아침에 KIS REST 호출은 없다. 08:55 실시간 연결은
개장 전이면 과거 분봉을 채우지 않는다.

**알고 두는 사각지대.** 보충 스윕은 풀 종목만 본다. 풀 밖 종목에서 07:00 뒤에 나온 뉴스는 그날 아침
목록에 들어가지 못한다. 전체를 다시 훑으면 2,648종목을 한 번 더 돌아야 한다. 실제로 문제가 되는지 본
뒤에 두 번째 전체 스윕을 판단한다.

**참고용 재계산(2026-09-25).** 9/21~9/23 아침을 그때까지 저장된 데이터로만 다시 계산하면 세 날 모두

### 9시 전 예상 갭 판정 (2026-10-06부터)

장전 동시호가의 예상체결가로 시가 갭 +3% 이상 종목을 9시 전에 목록에서 뺀다. 3개월 공시 표본에서 갭 +3% 이상 종목을 9시 시가에
사서 +2.5% 익절·손절 없음(비용 0.30% 뒤)은 평균 -1.38%(277건, t -3.9, 앞·뒤 절반 모두 마이너스), 우리 목록 5일도 매일
마이너스였다(소유자 결정, 2026-10-05).

- **08:50 판정**(`KisExpectedOpenCollector`, purpose `decide`): 목록 40개를 모두 조회해 `expected_open`에 남긴다(KIS
  `FHKST01010200` output2 원본 포함). 예상 시가 변화율은 `antc_cnpr / stck_sdpr - 1`로 직접 계산하고 KIS의

  +3% 이상이고 아직 남은 행(제외 이유 없음)이면 `excluded_reason`을 GAP_UP으로 바꾼다 — 08:38에 얼린 행을 바꾸는 유일한
  경우이고, 판단의 원본은 `expected_open`이다. 08:54가 지나면 반영하지 않는다(08:55 실시간 연결이 걸러진 목록을 읽게).

- **08:54쯤 카톡**: 두 번째 예약 작업이 `/api/briefing`에 `X-Briefing-Part:gap` 헤더로 부른다(같은 주소 — 기존 허용 규칙
  그대로). 응답의 `part`가 gap이 아니면 보내지 않는다. 판정이 아직 진행 중이면 서버가 최대 50초(08:54:50까지) 기다리고, 그래도

## 테마어 뉴스 (표시 전용, 2026-09-26)

```
python -m app.cli collect --source theme
```

종목 뉴스는 회사 이름으로 찾는다. 그래서 "AI 반도체 랠리"처럼 회사 이름 없이 테마로 쓰인 기사는 놓친다.
테마어 뉴스는 테마어 14개("AI 관련주", "반도체주", "HBM", "엔비디아", "원전", "전력기기", "2차전지", "방산",
"조선업", "로봇", "바이오주", "관세", "트럼프", "금리")로 네이버 뉴스를 찾아, 전날 한국 장 마감 뒤 기사 수와
그 기사에 이름이 나온 종목 상위를 센다. 07:00 체인 끝과 08:30 보충 끝에 돌고, "오늘의 관찰" 화면 위에 보인다.

- **표시 전용이다.** 발굴 점수, 후보 풀, 08:40 점수, 목록 순위 어디에도 들어가지 않는다. 밤사이
  업종 연구와 NXT 후속 연구는 이런 신호로 9시나 8시에 사서 비용 뒤·비교군 대비 남는다는 근거를 찾지
  못했다. 근거 없이 점수에 넣지 않는다. 테마 기사가 많다는 것은 "살 이유"가 아니라 "볼 곳"이다.
- **테마어는 초안이다.** 첫 실행(9/23 장 마감 ~ 9/26)에서 "조선주"는 7건, "로봇 관련주"는
  12건뿐이라 "조선업", "로봇"으로 넓혔다. "조선"은 신문 이름과 겹쳐 쓰지 않는다. 첫 실행에서는
  관세·트럼프·금리가 검색 API 상한 1,000건에서 잘렸다(창이 추석 연휴를 낀 약 71시간이었다. 평일
  07:00의 창은 약 15.5시간, 월요일은 약 63.5시간). 잘린 테마는 화면에 "+"로 표시한다.
- **언급 종목은 종목 뉴스와 같은 이름 판정(`judge`)을 쓰되 더 엄격하다.** 별칭·종목코드는 보지
  않는다. 회사 이름 검색에서는 검색어가 그 회사를 가리키지만, 테마 기사에서는 그렇지 않다. 그래서
  "주가·증시" 같은 약한 단서만으로 확인된 이름은 세지 않고, 첫 실데이터에서 보통 명사로 잡힌
  이름("디바이스", "미래산업")은 뺀다. 이름이 나왔다는 뜻이지 수혜주라는 뜻은 아니다.
- **호출:** 같은 네이버 검색 쿼터 그룹을 쓰고 원장에는 `news_theme`으로 따로 남는다. 첫 실행
  두 번은 한 번에 약 70~80회였고, 최대는 한 번에 140회(14개 × 10쪽)다. 수집 기록 이름은
  `THEME_NEWS`로, `NAVER_NEWS`로 시작하지 않는다(이름 앞부분으로 찾는 전체 스윕
  워터마크를 움직이지 않게).
- **체인 안의 위치:** 07:00 체인은 LLM 단계 다음에, 08:30 보충은 보충 LLM 다음에 돈다.
  뒤 단계는 이것을 기다리지 않는다. 07:00 LLM이 길어 08:50 목록이 먼저 얼거나 08:30 보충이
  포기하는 날은 그날 테마 뉴스가 없을 수 있다. 테마마다 커밋하므로 네이버가 도중에 실패해도 앞서 끝난
  테마는 남고 실행은 PARTIAL로 기록된다.
- **화면:** 기사 제목만 글자로 보이고 원문 링크는 두지 않는다(원문을 읽는 용도가 아니다).
- **저장:** `theme_news_day`에 하루·테마마다 한 행(08:30이 07:00 값을 덮어쓴다.
  08:30이 도중에 멈추면 나머지 테마는 07:00 값으로 남는다). 기사는 `news_item`에 넣지
  않고 최신 제목 5개와 언급 종목 상위 8개만 둔다. 과거로는 채울 수 없고(검색어당 최근 1,000건),
  쌓인 행은 나중에 앞으로의 기록으로 따로 검증할 수 있다.

  같다(전 한국 세션 마감 전 마지막 미국 종가 대비). 한국 연휴 뒤에는 누적이고 몇 일 치인지 날짜로 보인다.
  9/28은 9/23~9/25 미국 장 누적으로 필라델피아 반도체 -0.16%, 엔비디아 -1.66%, 마이크론 -1.27%였다.

**어디에도 점수로 들어가지 않는다.** 목록 선정, 08:40 채점, 목록 가설(H1~H7)은 그대로다. `list-review`는 대형주를
모든 묶음에서 빼고 따로 보여 주는 기술 통계이고 가설 판정이 아니다. 대형주를 뺀 묶음은 사전 등록 표본과 다르다.

## 전일 상한가 표시와 기록 (표시·사후 기록 전용, 2026-09-29)

목록 종목이 전 거래일에 상한가였으면 신호 카드와 오늘의 관찰에 표시한다. 전 거래일 일봉과 그 앞 봉의 종가(기준가격)로
판정한다(`app/scoring/price_limit.py`). 상한가는 기준가격의 30%를 호가단위로 내려 더한 뒤 결과 가격 구간 호가단위로
한 번 더 내린 값이다.

| 표시 | 뜻 |
|---|---|
| 전일 점상한가 | 시가·고가·저가·종가가 모두 상한가 |
| 전일 상한가 | 상한가로 마감, 장중 그 아래 거래가 있었다 |
| 전일 상한가 터치 | 장중 상한가에 닿은 뒤 그 아래에서 마감 |

화면에는 사실만 적는다. `list-review`는 이 세 묶음과 종목별 갭(그날 첫 1분봉 시가 / 전일 종가), 첫 1시간, 시가→종가를
따로 보여 준다. 9/29 목록에서는 HLB제약·HLB생명과학이 점상(갭 +26.2%, +16.6%, 시가→종가 -0.9%, -8.3%), HLB파나진이
상한가 마감(갭 +6.7%, 시가→종가 -15.9%), 베노티앤알·뷰노가 터치였다. 표본이 쌓이기 전에는 규칙으로 쓰지 않는다.

## 증권사 의견 (참고 표시, 2026-09-30)

```
python -m app.cli collect --source kis_opinion                         # 오늘 목록 종목
python -m app.cli opinion-backfill --days 2026-09-28,2026-09-29,2026-09-30
```

KIS 종목투자의견(`FHKST663300C0`)을 평일 08:40(2026-10-02부터, 그 전 08:53)에 그날 목록 종목만 받는다(종목당 1회, 183일). 한 행이 리포트 하나다.
`analyst_opinion`에 원문 그대로, `analyst_opinion_fetch`에 종목별 조회 기록(OK / TRUNCATED / FAILED)을 둔다.
목록 날 D의 요약은 D 전 90일 리포트로 낸다: 건수, 증권사 수, 증권사별 최신 목표가의 평균과 전일 종가 대비, 최근 리포트,
목표가 상향·하향 수. 신호 카드에는 리포트가 있을 때만, 오늘의 관찰 상세에는 "없음"까지 보인다. `list-review`는
"리포트 있음 / 없음(조회됨)"을 따로 묶는다. 점수·목록 선정에는 쓰지 않는다 — 표본이 쌓인 뒤 목표가 괴리와 결과를 본다.

## 뉴스·공시 쉬운 설명 (판단 보조, 2026-10-01)

목록 종목의 근거 뉴스·공시마다 세 가지를 붙인다. 오늘의 관찰 상세, 카톡 브리핑, `list-review`가 같은 값을 쓴다.
사라·팔라는 말하지 않는다 — 회사에 좋은 일인지와 지난 기록만 보여주고 판단은 사람이 한다.

- **무슨 일**: 공시는 제목 규칙(`disclosure_events.matched`가 맞힌 문구)의 쉬운 말(`scoring/event_explain.py`).
  뉴스는 아침 오버레이와 같은 모델·프롬프트(v2)가 읽은 근거 문장(`news_sentiment.evidence`, `asof` 전 저장분만). 없으면 제목.
- **좋은 일/나쁜 일**: 공시는 규칙(자회사 공시는 한 단계 약하게: 다소 좋음/다소 나쁨), 뉴스는 AI 감성 점수
  (±0.2 미만 애매, ±0.6 이상 좋음/나쁨). 어느 쪽이 정했는지(`verdict_source`)를 함께 보인다.
- **이런 일이 생기면 보통**: 9시 시가에 샀다고 치고 첫 1시간(`scoring/early_path.py`, 09:01부터 팔 수 있다고 봄)의 기록.
  +2.5%에 10분·1시간 안에 닿은 비율, 닿는 데 걸린 분(중앙값), 닿기 전 최저 평균(09:00 봉 안의 하락 포함 — 공시 연구의 MAE보다
  깊다), 못 닿았을 때 10시 평균.
  - 공시: 3개월 기준표 `app/reference/disclosure_reaction.json`(2026-06-30~09-21 진입일, 공시 연구 파일로
    `reaction-reference`가 만든다). 같은 공시가 10건 미만이면 같은 종류·방향 전체, 그것도 모자라면 "기록 부족".
  - 뉴스: 과거 뉴스 이력이 없어 우리 목록 기록만 쓴다(같은 종류·방향, 10건 이상일 때만).
  - 공시도 우리 목록 기록이 10건 이상 쌓이면 함께 보인다.
- 목록 이유가 공시인 종목은 전 거래일~전날 접수된 사건 공시 중 사건 칸에 없는 것을 앞에 덧붙인다(공시는 다음 개장부터 쓸 수
  있어 아침 오버레이의 공시 사건은 하루 늦은 옛 공시다). 설명을 붙이다 실패하면 설명 없는 원래 목록이 그대로 나가고,
  공시 덧붙이기·우리 목록 기록은 각각 따로 실패해도 나머지 설명은 붙는다.
- 카톡은 사건 하나를 200자 한 통에 담는다. 넘치면 우리 목록을 빼고, 남는 자리는 "왜"에 먼저 주고 "무슨 일"을 40자까지 줄인다.
  종목당 사건 둘까지(이유 공시가 먼저, 같은 종류·판단은 한 번), 원문 링크는 따로. 뉴스는 우리 목록 기록(10건 이상)이 "보통" 줄이 된다.
  읽는 법 안내는 설명이 붙은 날에만 한 통.
- `list-review`에 9시 시가 기준 +2.5% 10분·60분 도달률과 못 닿은 경우의 10시 평균, 시가 갭·지수 방향·공시 종류 묶음을 더했다.
